# 项目记忆链路与知识增强链路梳理

## 1. 梳理目的

本文档用于明确当前 `xiaozhi-server` 项目中与课题最相关的两条核心链路：

- 长期记忆链路
- 领域知识增强链路

后续系统改造、实验设计和论文实现，均以本梳理结果为基线展开。

## 2. 当前结论先行

结合当前代码和默认配置，可以先得到三个关键结论：

1. 当前系统在架构上已经具备“记忆注入 + 按需知识增强”的基础能力。
2. 当前默认配置下，这两条能力并未完全处于可用状态：
   - `data/.config.yaml` 中 `selected_module.Memory` 仍为 `nomem`
   - `Intent.function_call.functions` 中 `search_from_ragflow` 仍为注释状态
3. 因此，课题后续工作的重点不是从零开始搭建，而是围绕现有链路进行场景化启用、优化和验证。

## 4. 长期记忆链路梳理

### 4.1 入口与初始化

在 `core/connection.py` 中，会话对象在运行时持有 `memory` 模块，并在初始化阶段调用 `_initialize_memory()` 完成记忆模块装配。

关键位置：

- `core/connection.py:700` `def _initialize_memory(self)`

该函数主要完成以下工作：

1. 调用 `self.memory.init_memory(...)`
2. 传入当前设备或角色标识 `role_id`
3. 传入当前 LLM
4. 根据配置选择记忆实现类型
5. 在某些模式下为记忆模块设置独立 LLM

记忆模块的统一抽象定义在：

- `core/providers/memory/base.py`

其中统一接口只有三个核心点：

- `init_memory`
- `save_memory`
- `query_memory`

这意味着后续无论你是使用 `mem_local_short` 还是 `powermem`，对上层会话链路来说，调用方式是一致的。

### 4.2 对话时的记忆查询

在 `core/connection.py` 的 `chat()` 中，当用户本轮有真实输入 `query` 时，会优先查询记忆：

- `core/connection.py:846` `self.memory.query_memory(query)`

随后返回的 `memory_str` 会传给：

- `core/connection.py:854`
- `core/connection.py:862`

对应注入入口为：

- `core/utils/dialogue.py:62` `get_llm_dialogue_with_memory(...)`

该函数会把记忆字符串写入系统提示词中的 `<memory>` 标签位置：

- `core/utils/dialogue.py:105-107`

也就是说，当前系统的记忆使用方式并不是“把记忆作为普通消息插入对话历史”，而是：

- 先查询记忆
- 再把记忆结果整体注入系统提示词
- 最终由 LLM 在生成回答时统一参考

这正好适合后续课题中“长期记忆管理”的场景化改造。

### 4.3 对话结束时的记忆保存

在连接关闭前，系统会触发记忆保存：

- `core/connection.py:243` `_save_and_close`
- `core/connection.py:254` `self.memory.save_memory(...)`

当前实现采用后台线程异步保存，不阻塞关闭流程。也就是说：

1. 对话结束
2. 记录完整对话历史
3. 异步触发记忆保存
4. 保存失败不阻塞主流程

这个位置是后续“记忆抽取写入策略”最适合切入的地方。

### 4.4 当前支持的记忆实现

#### 4.4.1 `nomem`

文件：

- `core/providers/memory/nomem/nomem.py`

作用：

- 不保存记忆
- 不查询记忆

这是当前默认配置下的实际行为。

#### 4.4.2 `mem_local_short`

文件：

- `core/providers/memory/mem_local_short/mem_local_short.py`

主要特征：

1. 使用 LLM 对对话历史做总结
2. 将总结结果保存到本地 `data/.memory.yaml`
3. 查询时直接返回整段总结记忆

关键位置：

- `mem_local_short.py:103` 记忆文件路径
- `mem_local_short.py:135` `save_memory`
- `mem_local_short.py:200` `query_memory`

当前局限：

- 更偏“整段摘要式记忆”
- 查询阶段没有针对性检索
- 不区分任务状态、历史结论、用户偏好等不同记忆类型

但它很适合作为第一阶段最容易落地的实验基线。

#### 4.4.3 `powermem`

文件：

- `core/providers/memory/powermem/powermem.py`

主要特征：

1. 支持 `AsyncMemory` 或 `UserMemory`
2. 支持向量化记忆检索
3. 支持用户画像信息
4. 查询结果按时间整理后返回

关键位置：

- `powermem.py:154` `save_memory`
- `powermem.py:197` `self.memory_client.add(...)`
- `powermem.py:220` `query_memory`
- `powermem.py:253-269` 查询记忆与用户画像
- `powermem.py:324` `get_user_profile`

相较于 `mem_local_short`，`powermem` 更接近课题中“长期记忆管理”的目标，因为它已经具备：

- 记忆存储
- 记忆检索
- 用户画像
- 更细粒度的结果返回

如果后续实验条件允许，`powermem` 更适合作为论文主系统的长期记忆方案。

## 5. 领域知识增强链路梳理

### 5.1 插件注册与函数描述

项目启动时会自动导入插件目录：

- `core/connection.py:49`
- `plugins_func/loadplugins.py`

所有插件通过装饰器注册到统一函数注册表：

- `plugins_func/register.py`

`search_from_ragflow` 的注册定义在：

- `plugins_func/functions/search_from_ragflow.py:14`
- `plugins_func/functions/search_from_ragflow.py:31`

它的原始函数描述是：

- 函数名：`search_from_ragflow`
- 参数：`question`
- 作用：从知识库中查询信息

### 5.2 哪些函数会暴露给 LLM

工具是否真正出现在 LLM 可调用列表中，不取决于插件文件是否存在，而取决于配置中是否被启用。

关键逻辑在：

- `core/providers/tools/server_plugins/plugin_executor.py:57-92`

这里会把两部分函数合并：

1. 必要函数
2. 当前配置中的 `Intent.function_call.functions`

然后为每个函数生成给 LLM 使用的函数描述。

更重要的是，插件配置中的 `description` 会覆盖注册时的默认描述：

- `plugin_executor.py:78-89`

这就意味着：

- `data/.config.yaml` 中 `search_from_ragflow.description`
- 实际上就是你后续控制“知识增强何时触发”的关键入口

这也是你课题里“领域知识增强按需触发”的直接落点。

### 5.3 函数描述如何进入 LLM

在 `core/connection.py` 中：

- `core/connection.py:785` 创建 `UnifiedToolHandler`
- `core/connection.py:837` 调用 `self.func_handler.get_functions()`

得到的 `functions` 列表会传给：

- LLM 的 `response_with_functions(...)`

因此当前系统的知识增强链路是：

1. 工具处理器收集可用函数
2. 把函数描述传给 LLM
3. LLM 根据提示词和函数描述决定是否调用
4. 若调用 `search_from_ragflow`，则执行知识检索
5. 检索结果返回后再进入下一轮回答生成

### 5.4 `search_from_ragflow` 的执行逻辑

文件：

- `plugins_func/functions/search_from_ragflow.py`

关键逻辑：

1. 从配置中读取：
   - `base_url`
   - `api_key`
   - `dataset_ids`
2. 向 RAGFlow 的 `/api/v1/retrieval` 发起请求
3. 取回 `chunks`
4. 拼接成上下文文本
5. 返回 `ActionResponse(Action.REQLLM, context_text, None)`

关键位置：

- `search_from_ragflow.py:42` 读取数据集 ID
- `search_from_ragflow.py:48` 构造请求载荷
- `search_from_ragflow.py:52` 发送请求
- `search_from_ragflow.py:91-99` 提取 chunks
- `search_from_ragflow.py:111` 返回 `Action.REQLLM`

这说明当前知识库插件的工作方式不是“直接替 LLM 生成最终答案”，而是：

- 先检索
- 再把检索结果作为额外上下文返回
- 再由 LLM 基于该结果继续生成最终回答

这与课题中“领域知识增强”的思路完全一致。

### 5.5 提示词中的知识增强约束

在 `agent-base-prompt.txt` 中，工具调用规则已经明确写出：

- `agent-base-prompt.txt:55` `<tool_calling>`
- `agent-base-prompt.txt:71` 对 `search_from_ragflow` 的专门说明

同时系统提示词还预留了：

- `agent-base-prompt.txt:74` `<context>`
- `agent-base-prompt.txt:84` `<memory>`

这说明当前系统在提示词层面已经天然支持：

- 上下文信息注入
- 记忆信息注入
- 按需工具调用

所以从系统架构上看，你的课题主线与项目本身是高度匹配的。

## 6. 当前默认配置的真实状态

结合 `data/.config.yaml` 与 `config.yaml`，当前默认配置存在两个非常关键的问题。

### 6.1 记忆默认未启用

关键位置：

- `data/.config.yaml:225` `Memory: nomem`

这表示当前默认运行配置下：

- 不保存长期记忆
- 不查询长期记忆
- 对话中的 `<memory>` 实际上大概率为空

### 6.2 RAG 插件默认未启用

关键位置：

- `data/.config.yaml:162-164` 已配置 `search_from_ragflow`
- 但在 `Intent.function_call.functions` 中：
- `config.yaml` 和当前覆盖配置里 `search_from_ragflow` 仍是注释状态

也就是说：

1. 插件代码存在
2. 插件配置存在
3. 但函数列表中没有启用该函数
4. 因此 LLM 默认拿不到这个函数描述
5. 实际运行时就不会触发知识增强
